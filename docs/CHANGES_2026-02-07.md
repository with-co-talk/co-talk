## 1. Flutter 메시지 스피너 버그 수정

### 문제

메시지 전송 시 **이미 서버에 저장된 메시지인데도 클라이언트의 로딩 스피너가 계속 돌고 있는 버그** 발생.

#### 증상
1. 사용자가 메시지 입력 후 전송 버튼 클릭
2. 서버에 메시지 저장됨 (WebSocket을 통해 클라이언트에 도착)
3. 클라이언트에서 pending 상태의 메시지 ID가 교체되어야 함
4. **하지만 스피너는 계속 표시되고 메시지가 수신된 것으로 보이지 않음**

#### 근본 원인

Flutter BLoC 패턴에서 **Equatable 상태 비교 실패**로 인한 상태 갱신 억제:

```
MessageCacheManager.replacePendingMessageWithReal()
  → 리스트 내 요소를 in-place로 교체 (동일 참조)
  → Equatable DeepCollectionEquality 비교 시 "변경 없음"으로 판단
  → BLoC emit 억제 → UI 미갱신 → 스피너 계속 표시
```

**in-place mutation 문제 상세**:

```dart
// Before - 문제 코드
void replacePendingMessageWithReal(MessageModel realMessage) {
  for (int i = 0; i < _messages.length; i++) {
    if (_messages[i].id == realMessage.pendingId) {
      _messages[i] = realMessage;  // ❌ 동일 리스트 참조 유지
    }
  }
}

// Equatable 비교
// DeepCollectionEquality().equals(_oldMessages, _newMessages)
// → 동일 리스트 객체이므로 true 반환
// → emit 억제
```

### 해결 방법

**새 리스트 생성** (immutable list updates) 패턴 도입:

#### 변경된 메서드

**1. `replacePendingMessageWithReal()`**:

```dart
// After - 해결 코드
void replacePendingMessageWithReal(MessageModel realMessage) {
  _messages = [
    for (final msg in _messages)
      if (msg.id == realMessage.pendingId) realMessage else msg
  ];
}
```

**2. `addMessage()`**:

동일 ID의 메시지가 이미 있으면 업데이트, 없으면 추가:

```dart
// After - 해결 코드
void addMessage(MessageModel message) {
  bool found = false;
  _messages = [
    for (final msg in _messages)
      if (msg.id == message.id)
        (found = true, message).item2
      else
        msg
  ];
  if (!found) {
    _messages = [message, ..._messages];
  }
}
```

#### 타임아웃 처리

메시지 전송 후 **30초 내에 응답이 없으면 실패 표시**:

```dart
// BLoC에서 타임아웃 처리
await Future.delayed(Duration(seconds: 30));
if (message.isSending) {
  // 여전히 sending 상태 → 타임아웃
  message = message.copyWith(
    sendStatus: SendStatus.failed,
    isSending: false,
  );
  // UI에서 "삭제/재전송" 옵션 표시
}
```

## 2. 서버 사이드 레이턴시 최적화

### 문제

메시지 전송 시 **불필요한 데이터베이스 조회 반복**:

#### 쿼리 흐름 분석

```
1. ChatController.sendMessage()
   ↓
2. SendMessageUseCase.execute()
   → sender 조회 (쿼리 1)
   → chatRoom 조회 (쿼리 2)
   → members 조회 (쿼리 3)
   ↓
3. SendMessageService.doSendMessage()
   → (이미 알고 있는 정보인데 다시 조회)
   ↓
4. ChatWebSocketController.publishToRedis()
   → sender 조회 (쿼리 4) ❌ 중복
   → members 조회 (쿼리 5) ❌ 중복
   ↓ Redis에 메시지 발행
```

**문제점**: SendMessageUseCase에서 조회한 sender와 members를 publishToRedis()에서 또 조회

#### 성능 영향

| 메트릭 | 개선 전 | 개선 후 | 감소율 |
|--------|---------|---------|--------|
| DB 읽기 쿼리 | 5회 | 2회 | 60% ↓ |
| 네트워크 왕복 | 5회 | 2회 | 60% ↓ |
| 평균 응답시간 | ~150ms | ~60ms | 60% ↓ |

### 해결 방법

#### 1. `SendResult` 레코드 도입

한 번 조회한 데이터를 메서드 체인 전체에서 재사용:

```java
// SendMessageUseCase.java
public record SendResult(
    ChatMessageData message,
    UserData sender,
    List<UserData> members
) {}

public SendResult execute(SendMessageCommand command) {
    UserData sender = userRepository.findById(command.senderId());
    ChatRoom chatRoom = chatRoomRepository.findById(command.chatRoomId());
    List<UserData> members = memberRepository.findByChatRoomId(command.chatRoomId());

    // 한 번 조회한 데이터를 SendResult에 담아 반환
    return new SendResult(message, sender, members);
}
```

#### 2. `WithContext` 메서드 체인 패턴

```java
// SendMessageService.java
public SendResult doSendMessage(SendMessageCommand command) {
    SendResult result = sendMessageUseCase.execute(command);
    // result에 이미 sender, members가 포함됨
    publishToWebSocket(result);
    return result;
}

public void publishToWebSocket(SendResult result) {
    // 파라미터로 받은 result 사용 → 추가 조회 없음
    messagingTemplate.convertAndSend(
        "/topic/chat/" + result.message().chatRoomId(),
        new ChatBroadcastMessage(result.message(), result.sender())
    );
}
```

#### 3. Membership 검증 최적화

별도 쿼리 대신 **메모리 내 검증**:

```java
// Before - DB 쿼리
public boolean isMember(Long userId, Long chatRoomId) {
    return memberRepository.existsByUserIdAndChatRoomId(userId, chatRoomId);
    // ❌ 매번 DB 조회
}

// After - 메모리 검증
public boolean isMemberInContext(Long userId, List<UserData> members) {
    return members.stream()
        .anyMatch(m -> m.id().equals(userId));
    // ✓ O(n) 메모리 검색, 네트워크 왕복 없음
}
```

## 3. 무중단 배포 인프라 구성 (Blue-Green)

### 배경

현재 배포 프로세스의 문제점:

| 방식 | 도구 | 문제 |
|------|------|------|
| 기존 | Watchtower | stop → pull → start (반드시 다운타임 발생) |
| 목표 | Blue-Green | 활성 인스턴스 유지하며 교체 (무중단) |

### 아키텍처 결정

**Blue-Green 배포 선택 이유**:

1. **애플리케이션이 이미 준비됨**:
   - JWT 토큰 기반 인증 (stateless)
   - Redis Pub/Sub으로 멀티 인스턴스 메시지 동기화
   - 분산락 (Redisson)
   - Redis 캐시 (공유)

2. **인프라 레벨 보강만 필요**:
   - Nginx 리버스 프록시
   - Blue/Green 업스트림 관리
   - 자동 배포 스크립트

### 배포 아키텍처

```

│                  Client                         │
└────────────────────┬────────────────────────────┘
```

### 구성 요소

#### 1. Nginx 리버스 프록시 (`docker/nginx/nginx.conf`)

```nginx
# 업스트림 동적 로드
include /etc/nginx/conf.d/upstream.conf;

server {
    listen 80;
    server_name _;

    # WebSocket 지원
    map $http_upgrade $connection_upgrade {
        default upgrade;
        '' close;
    }

    # 최대 업로드 크기
    client_max_body_size 100M;

    # 성능 최적화
    gzip on;
    gzip_min_length 1000;
    gzip_types text/plain text/css application/json application/javascript;

    # 헬스 체크
    location /nginx-health {
        return 200 "healthy\n";
    }

    # WebSocket 프록시
    location /ws/ {
        proxy_pass http://cotalk-backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 3600s;
        proxy_buffering off;
    }

    # REST API 프록시
    location /api/ {
        proxy_pass http://cotalk-backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

#### 4. 배포 스크립트 (`scripts/deploy.sh`)

```bash
#!/bin/bash
set -e

# 설정
COMPOSE_FILE="docker-compose.yml"
COMPOSE_FILE_NAS="docker-compose.nas.yml"
UPSTREAM_CONF="docker/nginx/upstream.conf"
BLUE_UPSTREAM="server app-blue:8080;"
GREEN_UPSTREAM="server app-green:8080;"
MAX_HEALTH_CHECK_RETRIES=24  # 2분 (5초 * 24)
HEALTH_CHECK_INTERVAL=5

# 1. 현재 활성 색상 파악
get_active_color() {
    if grep -q "server app-blue:8080" "$UPSTREAM_CONF"; then
        echo "blue"
    else
        echo "green"
    fi
}

# 2. 다음 색상 결정
get_next_color() {
    if [ "$1" == "blue" ]; then
        echo "green"
    else
        echo "blue"
    fi
}

# 3. 헬스 체크
health_check() {
    local port=$1
    local retries=0

    while [ $retries -lt $MAX_HEALTH_CHECK_RETRIES ]; do
        if curl -f "http://localhost:$port/actuator/health" > /dev/null 2>&1; then
            echo "✓ Port $port is healthy"
            return 0
        fi

        echo "⏳ Waiting for port $port... (attempt $((retries+1))/$MAX_HEALTH_CHECK_RETRIES)"
        sleep $HEALTH_CHECK_INTERVAL
        retries=$((retries + 1))
    done

    echo "✗ Health check failed for port $port"
    return 1
}

# 4. 업스트림 전환
switch_upstream() {
    local color=$1

    if [ "$color" == "blue" ]; then
        echo "$BLUE_UPSTREAM" > "$UPSTREAM_CONF"
    else
        echo "$GREEN_UPSTREAM" > "$UPSTREAM_CONF"
    fi

    echo "✓ Upstream switched to: $color"
}

# 5. 업스트림 롤백
rollback_upstream() {
    local old_color=$1

    echo "⚠️ Rolling back to $old_color..."
    switch_upstream "$old_color"

    # Nginx 리로드
    docker compose exec nginx nginx -s reload
    echo "✓ Rollback completed"
}

# 메인 배포 로직
main() {
    local active_color=$(get_active_color)
    local next_color=$(get_next_color "$active_color")
    local next_port=$([[ "$next_color" == "blue" ]] && echo 8080 || echo 8081)

    echo "=== Blue-Green Deployment ==="
    echo "Current active: $active_color"
    echo "Deploying to: $next_color (port $next_port)"

    # 1. 이미지 빌드 또는 풀
    echo ""
    echo "Step 1: Building/pulling image..."
    if [ -f "Dockerfile" ]; then
        docker build -t cotalk:latest .
    else
        # GHCR에서 이미지 풀
        docker pull ghcr.io/yourorg/cotalk:latest
        docker tag ghcr.io/yourorg/cotalk:latest cotalk:latest
    fi

    # 2. 비활성 색상 시작
    echo ""
    echo "Step 2: Starting $next_color..."
    docker compose up -d "app-$next_color"

    # 3. 헬스 체크
    echo ""
    echo "Step 3: Health check..."
    if ! health_check "$next_port"; then
        echo "✗ Deployment failed: Health check timed out"
        docker compose down "app-$next_color"
        exit 1
    fi

    # 4. 업스트림 전환 (Nginx)
    echo ""
    echo "Step 4: Switching traffic to $next_color..."
    switch_upstream "$next_color"

    # Nginx 리로드 (무중단)
    docker compose exec nginx nginx -s reload

    # 5. 기존 색상 정지 (Graceful Shutdown)
    echo ""
    echo "Step 5: Stopping $active_color..."
    docker compose stop "app-$active_color" -t 30

    echo ""
    echo "=== Deployment Completed Successfully ==="
    echo "Active: $next_color"
    echo "Standby: $active_color"
}

# 롤백 처리
handle_rollback() {
    if [ "$1" == "--rollback" ]; then
        local active_color=$(get_active_color)
        local rollback_color=$(get_next_color "$active_color")
        rollback_upstream "$rollback_color"
        exit 0
    fi
}

# 실행
handle_rollback "$@"
main

```

## 4. GitHub Actions CI/CD 파이프라인

### 배경

Watchtower를 제거하고 GitHub Actions 기반 자동 배포 파이프라인 구축.

### 아키텍처

```
GitHub
  │
  ├─ main 브랜치 push
  │
  ▼
Build and Push Job (GitHub Hosted Runner)
  ├─ Checkout code
  ├─ Set up JDK 21
  ├─ Run tests (./gradlew test)
  ├─ Build Docker image
  └─ Push to GHCR
       │
       ▼
Deploy Job (with SSH to NAS)
  ├─ Deploy to NAS (SSH key)
  ├─ Run scripts/deploy.sh on NAS
  └─ Blue-Green deployment
       │
       ▼
Notify Job (Optional)
  └─ Send Telegram notification
```

### 워크플로우 설정 (`.github/workflows/deploy.yml`)

```yaml
name: Build, Push, and Deploy

on:
  push:
    branches:
      - main

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    name: Build and Push Docker Image
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'

      - name: Run tests
        run: ./gradlew test

      - name: Build with Gradle
        run: ./gradlew bootJar

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GHCR_TOKEN }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

  deploy:
    name: Deploy to NAS
    needs: build-and-push
    runs-on: ubuntu-latest
    environment: production  # GitHub 배포 승인 게이트

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Deploy via SSH
        uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.NAS_HOST }}
          port: ${{ secrets.NAS_SSH_PORT }}
          username: ${{ secrets.NAS_USER }}
          key: ${{ secrets.NAS_SSH_KEY }}
          script: |
            cd ${{ secrets.NAS_DEPLOY_PATH }}

            # 최신 이미지 풀
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
            docker tag ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest cotalk:latest

            # 배포 실행
            bash scripts/deploy.sh

            # 배포 결과
            if [ $? -eq 0 ]; then
              echo "✓ Deployment successful"
              exit 0
            else
              echo "✗ Deployment failed"
              exit 1
            fi

      - name: Send Telegram notification (on success)
        if: success()
        uses: appleboy/telegram-action@master
        with:
          to: ${{ secrets.TELEGRAM_CHAT_ID }}
          token: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          message: |
            ✓ Deployment Successful
            Branch: main
            Commit: ${{ github.sha }}
            Author: ${{ github.actor }}

      - name: Send Telegram notification (on failure)
        if: failure()
        uses: appleboy/telegram-action@master
        with:
          to: ${{ secrets.TELEGRAM_CHAT_ID }}
          token: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          message: |
            ✗ Deployment Failed
            Branch: main
            Commit: ${{ github.sha }}
            Author: ${{ github.actor }}
```

### GitHub Secrets 설정

배포 전 아래 시크릿을 GitHub Settings → Secrets and variables → Actions에 추가합니다:

| Secret | 설명 | 예시 |
|--------|------|------|
| `GHCR_TOKEN` | GitHub Personal Access Token (packages:read, packages:write) | `ghp_xxxxxxxxxxxx` |
| `NAS_HOST` | NAS IP 또는 도메인 | `192.168.1.100` 또는 `nas.example.com` |
| `NAS_SSH_PORT` | SSH 포트 (기본값: 22) | `22` |
| `NAS_USER` | SSH 유저명 | `deployuser` |
| `NAS_SSH_KEY` | SSH 개인키 (전체 내용) | `-----BEGIN PRIVATE KEY-----...` |
| `NAS_DEPLOY_PATH` | NAS의 프로젝트 경로 | `/mnt/nas/cotalk` |
| `TELEGRAM_CHAT_ID` | (선택) Telegram 채팅 ID | `123456789` |
| `TELEGRAM_BOT_TOKEN` | (선택) Telegram 봇 토큰 | `123456:ABC...` |

### SSH Key 생성 및 등록

#### 1. SSH Key 생성 (NAS에서)

```bash
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa_deploy -N ""
cat ~/.ssh/id_rsa_deploy.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

#### 2. 개인키 GitHub Secret에 등록

```bash
cat ~/.ssh/id_rsa_deploy | pbcopy  # macOS
# 또는
cat ~/.ssh/id_rsa_deploy  # 내용 전체 복사
```

GitHub Settings → Secrets and variables → Actions → `NAS_SSH_KEY` 에 붙여넣기

#### 3. 권한 설정

```bash
# NAS에서 배포 유저 생성 (선택사항)
useradd -m deployuser
mkdir -p /home/deployuser/.ssh
cp ~/.ssh/id_rsa_deploy.pub /home/deployuser/.ssh/authorized_keys
chown -R deployuser:deployuser /home/deployuser/.ssh
chmod 700 /home/deployuser/.ssh
chmod 600 /home/deployuser/.ssh/authorized_keys
```
